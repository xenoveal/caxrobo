# v0.3.2 — Pattern Detection Correctness

**Status:** in-progress
**Branch:** `fix/pattern-detection-correctness`
**Origin:** code review 2026-07-29. Four defects reproduced with fixtures; see
"Evidence" below. The visible symptom was a `double-bottom` emitted mid-rally
on BTCUSDT 4h, 2024-06-04, with a chart overlay that showed no W at all.

---

## Summary

Chart-pattern detection is producing shapes that are not the patterns they are
named after, and the UI cannot show the geometry because it was never persisted.
This plan fixes the geometry, adds the trend context the codebase deferred and
never built, and makes the replay chart draw the *real* pivots.

Four defects, each independently reproduced:

| # | Defect | Evidence |
|---|---|---|
| D1 | `_detect_double` has no prior-trend requirement — a +49% straight-line rally followed by an ordinary consolidation emits `double-bottom` | fixture reproduced |
| D2 | `_detect_double` has no "nothing lower in between" guard — lows at 88.58 / 89.33 with a **76.35** low between them (13.8% below both) still emits `double-bottom` | fixture reproduced |
| D3 | `min_trough_depth` has no maximum — lows 81.67 / 81.09 with a **+39% / 32-bar** rally between them emits `double-bottom`, `target_height` 32.50 | fixture reproduced |
| D4 | The replay chart's "pattern zone" is a hardcoded 20-bar × 34px rectangle centred on entry price (`ui/static/app.js:1937`); `Trade` never stores the detected geometry, so the UI has nothing real to draw | read directly |

Systemic root cause behind D1: three detector docstrings defer prior-trend
context to "a `Confirmation`'s job (Phase 4)"
(`continuation.py:27`, `:759`; `reversal.py`). `plugins/confirmations/` contains
only `macd` and `volume-breakout`. `RegimeGate` is ADX/ATR — trending-vs-ranging,
**not directional**. Trend context is checked nowhere in the pipeline.

Secondary: `fit_converging_lines` (`_geometry.py:236`) fits each boundary through
only the first and last pivot on that side, with `min_pivots_per_side` defaulting
to 2. Intermediate pivots are never required to *touch* the lines — `_contains`
only checks they don't exceed them. A "triangle" can be four pivots around empty
space.

## Non-negotiable constraints

1. **`src/trading_bot/signals/patterns.py` and
   `plugins/detectors/legacy_patterns.py` are FROZEN.** They exist to reproduce
   v0.2.0 exactly and are pinned by the Phase 3 parity test
   (`tests/test_framework_parity.py`). Nothing in this plan edits either file.
   `_geometry.py`'s module docstring states this explicitly — read it first.
2. **New geometry tests default to CORRECT, not to legacy-preserving.** The user
   asked for the bugs fixed, not flagged. Every new gate is a declared
   `ParamSpec` so it stays sweepable and can be turned off for A/B measurement,
   but the *default* is the correct behaviour. This will move detection counts
   and therefore backtest numbers — that is intended and must be stated in the
   report, not hidden.
3. **Detection reads OHLC, not closes.** A pattern lives in the candle range —
   wicks are where the rejections are. Any new test that reduces a bar to its
   close must justify it in a comment or use `high`/`low`. See "OHLC audit".
4. **No new dependencies.** `KNOWN-LIMITATIONS-v0.3.0.md §8` forbids adding an
   indicator library; hand-roll into `src/trading_bot/indicators/` if needed.
5. **Do not stage `src/trading_bot/ui/server.py` or the pre-existing hunks in
   `src/trading_bot/ui/api.py` / `tests/test_ui_api.py`** — unrelated
   in-progress work is in the tree. Never `git add -A`.

## Workstreams

Three parallel workstreams, partitioned so no two agents touch the same file.

### WS-A — Reversal geometry hardening (D1, D2, D3 + OHLC audit)

**Owns:** `src/trading_bot/plugins/detectors/reversal.py`,
`src/trading_bot/config.py`, `tests/test_detectors_reversal.py`

Fix `_detect_double` so a double top/bottom is the shape its name claims:

- **D2 — dominance guard.** Between the two extremes, no bar may trade beyond
  either extreme. For a double bottom: `lows[a.index : b.index + 1].min()` must
  not be below `min(a.price, b.price)` by more than a declared tolerance.
  Use the bar `low` array, not pivots and not closes — a pivot-based check
  misses an unconfirmed spike. Mirror for the top.
- **D3 — maximum trough depth.** Add `max_trough_depth` alongside the existing
  `min_trough_depth`, same units (fraction of the mean extreme). A W whose
  middle bump exceeds it is a range, not a pattern.
- **D1 — prior-trend requirement.** A double bottom must reverse *something*.
  Require a measurable decline into `a` over a declared lookback, expressed as
  a fraction of price. Implement it here as a detector-local gate; WS-C's
  Confirmation is the *pipeline-wide* answer and the two are complementary, not
  duplicates — this one shapes what the detector emits, WS-C's gates what
  survives to a trade.
- Consider whether `dedupe_events` keeping the **largest target** is right once
  these gates land (it currently selects the widest, sloppiest pair). If you
  change it, say so loudly in the report — it is shared by every detector.

Every new gate: a `ParamSpec` with `doc`, bounds, and a `config.py` default in
the existing `DOUBLE_*` block. Follow the file's own conventions exactly —
the module has a strong, deliberate documentation style; match its density and
its habit of naming the failure mode a test prevents.

**OHLC audit (same workstream, `reversal.py` scope only):** `level_unbroken`
in `_geometry.py` tests `close` only. Assess whether that is correct for these
detectors or whether an intrabar `high`/`low` breach should also spend the
pattern. **Do not edit `_geometry.py`** — it is shared with the frozen-parity
surface. Write your finding into the report and, if a change is warranted,
implement it as a local helper in `reversal.py`.

**Tests:** port the four reproduction fixtures below into
`tests/test_detectors_reversal.py` as rejection tests, each docstring naming the
real failure mode it prevents (the file's established style, per its header).
Plus at least one *acceptance* test proving a genuine W still fires — a
regression that silently detects nothing is worse than the bug.

### WS-B — Persist pattern geometry and draw it (D4)

**Owns:** `src/trading_bot/backtest/engine.py`,
`src/trading_bot/framework/execute.py`, `src/trading_bot/ui/api.py`,
`src/trading_bot/ui/static/app.js`, `tests/test_ui_api.py`,
`tests/test_backtest.py`

The chart lies because the data is not there. Fix the pipeline end to end:

- `Trade` (`engine.py:109`) gains the detected geometry: the event's
  `start_ts`, `end_ts`, `level`, and the `meta` keys that describe the shape
  (`peak_a` / `peak_b` / `trough` for doubles, `head` / `left_shoulder` /
  `right_shoulder` for H&S, etc.). Follow the precedent already set by the
  "LAST THREE FIELDS ARE THE AUDIT TRAIL" block in that docstring: new fields
  are **graph-path only**, default to empty, and `run_backtest` leaves them at
  defaults so `tests/test_framework_parity.py` stays bit-identical. Read that
  docstring and `contract §5` before writing.
- `execute.py` populates them at the `Trade(...)` construction site (~line 239).
- `_serialize_trades` (`api.py:764`) passes them through. Additive and
  presentational only — that function's docstring already states the rule.
- `app.js` `evoDrawTrade` (line ~1928) draws the **actual** geometry: the zone
  spans `start_ts`→`end_ts` and its vertical extent is the real pivot prices.
  Mark the pivots. The existing comment at line 1937 admitting the box is an
  approximation gets deleted, because it stops being true.
- Degrade honestly: a trade with no geometry (legacy rows, `run_backtest` path)
  must render *without* a zone rather than falling back to the fake box.

**Reference for what "right" looks like:** a clean schematic where the drawn
lines are the pattern's own structure — the two lows, the neckline, the
measured move. Aim at that, not at a shaded band.

### WS-C — Trend-context Confirmation (systemic root cause)

**Owns:** `src/trading_bot/plugins/confirmations/trend_context.py` (new),
`tests/test_plugins_confirmations.py`

Build the Confirmation that three docstrings promised and nobody wrote: a
directional prior-trend check that gates reversal patterns against the move they
claim to reverse, and continuation patterns against the trend they claim to
continue.

- Read both existing confirmations (`macd.py`, `volume_breakout.py`) first and
  mirror their structure, `@register` call, `ParamSpec` block and docstring
  style exactly.
- Return a `ConfirmationVerdict` with a populated `score` and a useful `reason`
  — the contract says `reason` is "most useful when passed is False", so make
  failures diagnosable.
- **Read every default from inline literals, not `config.py`.** This is the
  `rising-wedge` precedent (`continuation.py:346-361`) and it is also a hard
  merge-conflict constraint here: WS-A owns `config.py` this cycle.
- Direction semantics: reversal kinds (`double-bottom`, `inverse-head-and-shoulders`,
  `cup-and-handle`...) want the *opposite* prior trend; continuation kinds
  (`bull-flag`, `ascending-triangle`...) want the *same*. Derive this from the
  event `kind` explicitly and testably — a lookup the tests can enumerate, not
  a string heuristic scattered through branches.
- Measure trend from OHLC over a declared lookback on the setup timeframe.
